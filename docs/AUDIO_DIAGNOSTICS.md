## Linux 复测

烧录后重新连接 USB，运行以下命令，输出中应出现 `bcdDevice 1.03`：

```bash
sudo lsusb -v -d cafe:babe | grep bcdDevice
```

把 `tools/audio_monitor.py` 复制到 Linux 当前目录，播放会出现问题的音频，运行：

```bash
sudo python3 audio_monitor.py --seconds 60 | tee audio_diag_1.03.txt
```

脚本仅使用 Python 标准库，通过 hidraw 读取 HID，不需要安装 hidapi。
默认查找唯一的 CAFE:BABE 设备；多设备时用 `--device /dev/hidrawN` 指定。
若显示没有诊断报告，请检查固件版本和设备选择。

另开终端，在播放期间获取实际运行参数（声卡编号可能改变）：

```bash
cat /proc/asound/card*/stream*
```

请提供日志和参数，并记录杂音大约发生在监测开始后的第几秒。
`Status: Stop` 只能说明接口支持哪些格式，不能说明实际播放格式。
1.03 最高支持 96 kHz；当前版仅 Type III 透传增加 192 kHz 载波，PCM 仍最高 96 kHz。
无论哪个版本，192 kHz 源文件都不能作为 USB 实际工作于 192 kHz 的证据。

## 计数解释

HID 描述符轮询间隔为 200 ms，四页循环；主机实际调度间隔可能不同，
以脚本时间戳为准（用户的 Linux 日志约每 128 ms 一页）。
计数从芯片启动累计，停止播放不清零；脚本括号中的 `+` 是该字段相邻报告的增量。
不同字段并非同时采样，因此不用于精确的跨字段时序比较。

| 字段 | 含义 |
| --- | --- |
| underruns | 输入缓冲不足，进入恢复状态的次数 |
| dropped_frames | 输入缓冲溢出丢弃的立体声帧数 |
| silence_blocks | 输出 DMA 没有准备好的块，改用静音的次数 |
| spdif_stalls / i2s_stalls | 检测到对应 PIO TX 停顿的 DMA 间隔数 |
| bad_packets | 长度超限或未按完整立体声帧对齐的 USB 音频包数 |
| sample_rate | 固件当前配置的采样率，不是引脚频率测量值 |
| rx_packets / rx_frames | 固件收到的合法音频包数 / 立体声帧数 |
| rx_queue_drops | USB 收包中断无法保存或入队的包数；两个 reserved 字段保留为零 |

启动和停止附近的静音计数不能直接认定为故障，应重点比较持续播放中杂音前后的增量。
若计数均未异常增长，仍需检查音频内容、主机处理及输出时钟，不能据此排除所有固件问题。
I2S 单输出构建暂不提供后端 DMA/PIO 计数，相应字段为零。

HID 输入由原来的全零占位报告改为：`AD`、版本字节 `1`、页号 `0..3`、
三个小端 32 位整数，共 16 字节。该版本字节是诊断协议版本，不是 USB 固件版本。
无串口实时打印；USB 音频格式和双输出路由未改变。

## 1.03 接收修正及依据

1.02 的用户日志中，13.78–14.93 秒欠载计数从 609 增至 669，
27.22–28.37 秒再次集中增长。正常每约 384 ms 收到 384 包，异常期间只收到
约 255–260 包，每包仍约 96 帧。PIO 停顿和溢出未增长。
这确认了输入供数不足，但不能单凭接收计数判断主机少发还是设备未及时接收。

1.03 将音频 OUT 的数据复制和下一包接收准备移到 USB 中断，
避免等待主循环的样本转换、增益处理和 SPDIF 编码。
USB 事件队列保存完整包副本；格式切换、停止及总线复位通过代次标记丢弃旧包。
队列积压时丢弃新音频包并计数，保留位置给控制及反馈事件。
事件存储改为静态分配，避免较大包副本消耗中断栈；队列增加约 13 KB 堆内存开销。
原有 132 MHz 时钟、反馈算法和音频缓冲水位保持不变。

`rx_queue_drops` 是否增长，以及正常收包频率是否保持。1.02 的独立 UF2 文件保留。
